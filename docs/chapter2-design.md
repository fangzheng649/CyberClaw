# 第二章 设计思路与方案

## 2.1 系统总体架构

### 2.1.1 五层架构设计

CyberClaw采用分层解耦的五层架构设计，自底向上分为基础设施与数据源层、MCP安全工具服务层、安全应用服务层、AI安全决策与编排层和智能交互展示层。五层架构的核心设计思想是“关注点分离”——每一层只负责一个维度的逻辑，层与层之间通过标准化接口通信，使得任意层内部实现的变更不影响其他层。

> **【图2-1】系统整体架构图** — 纵向五层条带布局，每层使用不同底色（浅绿→浅蓝→浅青→浅橙→浅紫）。第1层（展示层）：自然语言对话通道 + 3D安全HUD并列；第2层（AI编排层）：ReAct循环中心 + Skills编排模块；第3层（应用服务层）：CyberScan/CyberSense/CyberShield/CyberReview四个引擎横排；第4层（MCP工具层）：12个MCP服务器按感知/检测/响应/复盘四类分组；第5层（基础设施层）：GNS3仿真 + 物理IoT设备。各层间用箭头连接，右侧纵贯红色虚线标注"WebSocket实时事件回推"。可复用初赛文档图1，更新为五层结构。

**（1）智能交互展示层**提供双通道用户交互。自然语言对话通道基于CyberAgent智能对话引擎实现，用户可直接用中文提问（如"分析这台摄像头的漏洞"），AI自动完成分析并以自然语言报告；对话引擎集成大语言模型（DeepSeek）进行语义理解和结果分析，同时通过正则意图匹配机制自动编排12个MCP安全工具执行扫描、检测和响应操作。3D安全HUD通道基于Three.js WebGL渲染引擎和WebSocket实时推送构建，采用五通道后处理管线（基础渲染→辉光效果→运动拖尾→胶片噪点→抗锯齿），以三维可视化呈现全网设备拓扑、安全状态着色、攻击路径光束和AI分析过程。两个通道共享同一套安全引擎和状态模型，通过BroadcastChannel API实现跨标签页实时状态同步。

**（2）AI安全决策与编排层**是系统的智能中枢。CyberAgent基于ReAct推理循环，通过“思考→行动→观察”的迭代实现动态策略调整。Skills以声明式定义安全分析流程，系统提示词（System Prompt）内置安全约束规则和操作规范。该层同时管理三层记忆架构（短期对话记忆 + 工作任务记忆 + 长期向量知识库）和多Agent协作调度。

**（3）安全应用服务层**包含四个按安全闭环阶段划分的设计引擎。CyberScan负责网络感知与设备发现；CyberSense负责多源数据采集与智能关联分析；CyberShield负责自动隔离与安全响应；CyberReview负责攻击时间线构建与根因分析。每个引擎封装特定安全领域的业务逻辑，将Skills的编排指令转化为对MCP工具的有序调度。

**（4）MCP安全工具服务层**基于MCP协议构建，包含12个独立的MCP服务器，提供约100个标准化安全工具。MCP采用JSON-RPC 2.0消息格式通过stdio管道传输，每个服务器遵循“单一职责”原则。工具动态加载机制在运行时通过反射自动发现和注册每个服务器暴露的工具函数，新增安全工具只需编写MCP服务器并注册配置即可即插即用。

**（5）基础设施与数据源层**由GNS3网络仿真环境和物理IoT设备共同构成，通过多协议适配（SSH/gNMI、Syslog/SNMP、NetFlow/IPFIX、tshark）连接上层工具服务。

### 2.1.2 安全闭环设计理念

CyberClaw以"感知→检测→响应→复盘"四阶段闭环为核心理念。四阶段闭环并非简单的线性流水线，而是具备反馈和迭代能力的循环结构：感知阶段的设备资产信息是检测阶段关联分析的数据基础；检测阶段的威胁判定触发响应阶段的自动处置；响应阶段的操作效果通过验证反馈至检测阶段进行二次确认；复盘阶段从全局视角提取攻击模式和防御薄弱点，反哺至感知阶段优化监控策略。

> **【图2-2】安全闭环架构图** — 环形/圆形循环图，中心放置CyberAgent六边形，四角放置四个阶段（感知/检测/响应/复盘），顺时针粗箭头连接，复盘→感知用虚线表示反馈。各阶段间标注数据流内容（设备资产清单、威胁判定结果、操作记录、监控策略优化）。右侧附注3D HUD实时同步机制。可复用初赛文档图2设计。

### 2.1.3 设计原则

系统设计遵循三个核心原则：（1）**协议驱动、接口标准化**——MCP协议定义统一的工具注册、发现和调用规范，新增安全工具零代码即可接入；（2）**声明式编排、逻辑可维护**——Skills以Markdown格式声明式定义，安全分析师无需编程即可编写新的分析流程；（3）**安全约束内置、操作可追溯**——三级权限控制（只读/确认写/禁止），所有操作通过action_id(UUID)关联审计日志，满足《网络安全法》六个月日志留存要求。

## 2.2 CyberScan 网络感知引擎

### 2.2.1 多模式网络扫描策略

IoT网络中设备类型多样，网络行为各异——部分设备响应ICMP探测，部分仅开放TCP端口，还有部分通过ARP可达但不响应更高层探测。单一扫描协议无法覆盖所有设备。CyberScan设计支持四种扫描模式：ICMP Echo探测（快速发现活跃主机）、TCP SYN半开扫描（绕过部分防火墙）、UDP端口扫描（发现DNS/DHCP等UDP服务）和ARP局域网扫描（发现不响应IP层的设备）。CyberAgent根据目标网段特征自动选择最优扫描组合——对于局域网场景优先使用ARP扫描（速度最快、准确率最高），对于跨网段场景组合ICMP+TCP SYN。

### 2.2.2 IoT设备指纹识别算法

准确识别IoT设备类型是后续检测和响应的基础。传统的单一信号识别方式（如仅依赖MAC地址厂商前缀）准确率有限。CyberClaw设计了**四维度加权融合**的指纹识别策略：

**Score(T) = 0.20 · S_OUI(T) + 0.45 · S_Banner(T) + 0.35 · S_Port(T)**

其中 S_OUI 为MAC地址厂商前缀匹配得分，S_Banner 为服务Banner解析得分（HTTP标题、SSH版本字符串、RTSP响应头等），S_Port 为端口组合模式匹配得分（如80+554组合高度指示摄像头，80+443+8080指示门禁设备）。**第四维度"综合判定"**为前三项加权融合后的阈值判定过程——当综合得分超过0.6时输出设备类型判定，低于0.6时触发深度分析模式。权重分配基于实测数据校准：Banner信息直接反映设备身份，权重最高（0.45）；端口模式次之（0.35）；MAC OUI因部分IoT设备使用通用网卡芯片而可靠性较低（0.20）。

算法设置0.6的判定阈值——当综合得分超过0.6时输出设备类型判定；低于0.6时触发深度分析模式，追加Nmap服务识别脚本（NSE）和HTTP指纹探测。四维度融合的设计使指纹识别具备容错能力：即使某一维度的信号缺失，其余维度仍能提供有效的识别依据。

> **【图2-3】IoT设备指纹识别四维度融合算法图** — 中心为加权融合公式，左侧三个输入源（MAC OUI/0.20、Banner解析/0.45、端口模式/0.35），中间为加权评分模块，右侧为阈值判定（≥0.6输出判定 / <0.6触发深度分析），底部展示判定结果（设备类型+厂商+置信度）。

### 2.2.3 默认密码检测

IoT设备出厂即携带默认凭证是IoT安全中最普遍也最危险的风险因素。CyberClaw在感知阶段集成默认密码检测能力，构建了通用50组+厂商特定70组的凭证库。检测采用分层策略：首先通过服务识别判断设备开放的管理协议（Telnet/SSH/HTTP），然后针对不同协议使用对应的检测方法（Telnet/SSH使用hydra封装尝试登录，HTTP使用POST表单检测），最终将凭证安全状态（安全/使用默认密码/无法检测）作为设备资产画像的核心字段。

### 2.2.4 设备配置管理

通过device-config MCP服务器，平台可经SSH或gNMI协议连接可管理网络设备，查询接口状态、CDP/LLDP邻居信息，构建网络拓扑关系。配置管理支持三种操作模式：查询模式（只读获取设备配置）、对比模式（差异检测配置变更）、下发模式（需用户确认后执行配置修改）。

### 2.2.5 自主设备发现与动态建档

CyberClaw设计了自主设备发现机制，实现网络中新增IoT设备的自动识别和动态建档。发现流水线采用**三层Fallback策略**：优先使用ARP扫描（arp-scan）获取局域网设备列表；若ARP不可用则降级为Nmap快速扫描（TCP SYN常用端口）；若前两种主动扫描均不可用，则从拓扑数据库中加载已知的设备信息（拓扑数据库在系统启动时从初始配置文件引导，运行时通过周期扫描和CDP/LLDP邻居发现持续更新，确保新接入网络的设备能被及时感知）。

发现流水线包含六个处理阶段：（1）设备创建——为每个发现的IP创建基础设备记录；（2）厂商识别——通过MAC OUI查询匹配19家IoT厂商MAC前缀库；（3）类型推断——应用22条JSON启发式规则推断设备类型；（4）属性填充——聚合端口、服务、Banner等信息；（5）拓扑关联——通过CDP/LLDP邻居信息建立设备间连接关系；（6）事件通知——将新设备发现事件推送至3D HUD和安全状态模型。

## 2.3 CyberSense 智能检测引擎

### 2.3.1 多源异构数据采集架构

检测层的核心设计理念是“多维证据的交叉关联胜过单一规则的机械匹配”。CyberSense设计了五路异构数据源并行采集架构：

> **【图2-4】多源异构数据采集架构图** — 左侧五个并列数据源（Syslog/SNMP Trap/MQTT/IPFIX/Suricata IDS），中间为采集引擎层（各自标注协议和解析方式），右侧汇聚至CyberSense关联分析引擎，底部标注数据流向。

（1）**Syslog采集器**：监听UDP 514端口，遵循RFC 5424格式解析，设计哈希去重机制避免重复告警、令牌桶限流防止告警风暴。（2）**SNMP Trap采集器**：支持SNMP v1/v2c/v3三个版本，将OID映射为可读事件名称。（3）**MQTT监控器**：监控IoT设备的MQTT通信，检测异常发布率（疑似数据外泄）和未授权主题订阅。（4）**IPFIX/NetFlow流量采集器**：支持v5/v9/v10三种版本，设计模板缓存机制处理NetFlow v9的动态模板，输出Top-N排行和异常流量检测。（5）**Suricata IDS事件监控**：实时提取IDS告警事件。

### 2.3.2 CVE漏洞关联查询

CVE查询模块设计了**CPE 2.3自动构造算法**——根据设备指纹识别结果（厂商、产品名、版本号）自动构造标准化的CPE 2.3标识符（如`cpe:2.3:h:hiwatch:ip_camera:2.0:*:*:*:*:*:*:*`），然后调用NVD API 2.0查询关联漏洞。查询结果通过SQLite缓存层（5分钟TTL）加速重复查询，API调用采用令牌桶限流和429状态码退避重试策略，保障在高并发场景下的服务稳定性。查询结果包含CVE编号、CVSS v3.1评分、影响版本范围和已知利用状态（KEV目录）。

### 2.3.3 安全基线审计

基线审计模块基于CIS（Center for Internet Security）标准设计了四种安全Profile（摄像头、路由器、服务器、通用IoT），涵盖49条检查规则。审计内容包括：默认密码检测、不安全协议识别（Telnet/FTP）、管理接口暴露检查、固件版本合规验证等。TCP端口扫描验证确保审计结果的准确性。每台设备输出合规评分（0-100）和不合规项清单，支持按设备类型和网段维度聚合分析。

### 2.3.4 AI多源关联检测策略

CyberSense的核心差异化设计是基于ReAct推理循环的智能关联分析。推理过程采用**七轮迭代策略**，每轮执行Thought→Action→Observation三个阶段：

| 轮次 | 推理目标 | 调用工具 | 输出 |
|:----:|:------:|:------:|:---:|
| 1 | 读取告警上下文 | attack-timeline | 事件详情+设备信息 |
| 2 | 扫描设备暴露面 | nmap-scan | 开放端口+服务识别 |
| 3 | 关联已知漏洞 | cve-intel | CVE列表+CVSS评分 |
| 4 | 检查配置合规 | security-baseline | 基线违规项+合规评分 |
| 5 | 分析网络流量 | flow-analyzer + traffic-analyzer | 异常流量+IoC指标 |
| 6 | 提取攻击指标 | traffic-analyzer | C2回连/横向移动/数据外泄 |
| 7 | 综合判定 | CyberAgent推理 | 攻击类型+置信度+响应建议 |

> **【图2-5】AI多源关联检测策略图** — 左侧四路数据源（设备日志/CVE情报/安全基线/网络流量），中间为ReAct七轮推理循环（标注每轮的Thought→Action→Observation），右侧输出（威胁判定/影响评估/响应建议）。底部展示动态策略调整示例：高风险走全7轮，低风险3-4轮即可判定。可复用初赛文档图3，增加七轮推理标注。

关键设计是基于**证据充分性的动态策略调整**：当第3轮CVE查询发现CVSS 9.8漏洞且已有公开利用代码时，Agent自动追加流量分析和基线检查（走完全部7轮）；当第3轮未发现高危漏洞时，Agent可跳过第5-6轮的深度流量分析，直接给出低风险判定（3-4轮完成）。这种动态调整在保证分析深度的同时避免了不必要的工具调用开销。

## 2.4 CyberShield 自动响应引擎

### 2.4.1 事件驱动自动响应架构

CyberShield设计了事件驱动的自动响应架构，实现从“被动告警”到“主动防御”的转变。响应架构的核心数据流为：

**安全事件 → NotificationBridge事件总线 → 策略评估引擎（规则匹配）→ 置信度计算（阈值判定）→ 分级响应决策**

当安全事件（Syslog告警/SNMP Trap/IDS告警）到达NotificationBridge事件总线时，系统首先进行策略评估——根据事件类型匹配预设的响应策略映射表（如Mirai感染→端口隔离+ACL封禁，C2回连→隔离+封禁C2服务器，暴力破解→ACL封禁源IP）。随后计算响应置信度——综合AI分析结论的置信度评分（c_ai）、历史同类事件的准确率（c_hist）和设备业务重要性权重（w_biz），通过加权公式 **C = 0.5 · c_ai + 0.3 · c_hist + 0.2 · w_biz** 生成综合置信度。最后根据置信度进行分级决策：

- **Critical + 置信度≥阈值**：自动隔离 + 实时通知用户
- **High**：生成处置建议 + 等待用户确认后执行
- **Warning/Info**：仅告警通知，不执行响应操作

> **【图2-6】事件驱动自动响应架构图** — 从左到右的数据流：安全事件源→NotificationBridge事件总线→策略评估引擎（策略映射表+置信度计算）→分级决策（Critical/High/Warning三级）→响应执行（自动隔离/建议确认/仅告警）。底部标注响应策略映射表的具体映射关系。

### 2.4.2 响应策略与分级决策

响应策略的设计遵循“最小影响原则”——在有效遏制威胁的同时最大限度减少对合法业务的影响。策略映射表根据攻击类型预定义响应动作：

| 攻击类型 | 响应策略 | 影响范围 | 需确认 |
|:------:|:------:|:------:|:-----:|
| Mirai/DDoS感染 | 端口隔离 + ACL封禁出站 | 单台设备 | Critical自动/High确认 |
| C2回连 | 设备隔离 + 封禁C2服务器 | 单台+外部IP | 需确认 |
| 暴力破解 | ACL封禁源IP | 源IP地址 | 自动执行 |
| 横向扫描 | 网段隔离 + 告警 | 整个网段 | 必须确认 |
| 配置篡改 | 配置回滚 + 审计 | 单台设备 | 需确认 |

每条响应记录生成唯一action_id(UUID)，贯穿“触发→评估→执行→验证→回滚”全生命周期，实现"who did what why"的完整审计追溯。

### 2.4.3 多厂商设备隔离方案

IoT网络中设备品牌多样，不同厂商的可管理交换机使用不同的CLI命令语法。CyberShield设计了**多厂商适配的隔离执行层**，采用双重隔离策略：

**策略一：iptables本地防火墙隔离**（默认策略）。通过Linux iptables在转发链（FORWARD链）双向插入DROP规则，分别针对源IP（-s）和目的IP（-d）阻断流量。系统自动检测WSL环境，在Windows部署场景下通过`wsl -e`前缀执行iptables命令。每条规则维护在内存字典中，隔离时创建、恢复时删除，确保规则生命周期可追踪。

**策略二：SSH交换机端口隔离**（企业级策略）。通过netmiko/paramiko库建立SSH连接至可管理交换机，执行对应厂商的CLI命令关闭目标设备所在端口。当前支持三家主流厂商的命令适配：

| 厂商 | 操作系统 | 端口关闭 | ACL下发 | 配置保存 |
|:---:|:------:|:------:|:-----:|:-----:|
| 华为 | VRP V5/V8 | interface shutdown | traffic-filter inbound | save |
| Cisco | IOS/IOS-XE | interface shutdown | ip access-group in | write memory |
| H3C | Comware V7 | interface shutdown | packet-filter inbound | save force |

**策略降级机制**：当iptables不可用且SSH连接失败时，系统降级为`record_only`模式，将隔离意图记录至审计日志但不执行实际操作，避免在不可控环境下造成误操作。设备IP到交换机端口的映射关系通过多源融合自动获取——系统优先通过SSH查询交换机MAC地址表（show mac address-table）动态发现设备与端口的对应关系，同时结合CDP/LLDP邻居信息和初始拓扑配置进行交叉验证。隔离执行前检查命令是否已存在（避免重复执行），隔离后自动执行ping不可达检测和端口扫描验证隔离效果。多厂商适配的具体实现见第三章。

### 2.4.4 四步安全响应流程

CyberShield的响应操作遵循“基线→隔离→验证→回滚”四步安全流程：

> **【图2-7】四步安全响应流程图** — 横向四步流程图。步骤1：基线采集（get_baseline）——记录当前网络连通性、活跃连接、接口状态；步骤2：隔离执行（isolate+block）——选择隔离策略并执行；步骤3：效果验证（verify_isolation）——ping不可达+端口扫描确认；步骤4：自动回滚（rollback）——验证失败时恢复原始状态。四步之间用箭头连接，步骤3有两条分支（验证成功→结束 / 验证失败→步骤4回滚）。

**步骤1：基线采集**——在执行任何隔离操作之前，通过auto-response MCP服务器采集目标设备的当前状态（网络连通性、活跃连接、接口状态），建立操作前的基准快照，为后续回滚提供恢复依据。

**步骤2：隔离执行**——根据威胁类型选择隔离策略。设备级隔离通过SSH连接交换机关闭对应端口；网络级隔离通过下发ACL规则封禁特定IP或端口。隔离操作通过netmiko/asyncssh库建立SSH连接。

**步骤3：效果验证**——隔离操作完成后，自动执行ping不可达检测和TCP端口扫描，确认目标设备已被成功隔离。验证结果记录至审计日志。

**步骤4：自动回滚**——若验证步骤发现隔离失败（如设备仍可达），系统自动触发回滚操作恢复原始状态。回滚操作基于步骤1采集的基线快照，确保恢复至操作前的精确状态。

### 2.4.5 配置合规审计

config-audit MCP服务器提供防火墙和ACL规则的合规审计能力。审计从三个维度检测规则问题：（1）**冲突检测**——新下发规则与现有规则的语义矛盾；（2）**重叠检测**——多条规则覆盖相同的流量范围，可能导致不可预测的过滤行为；（3）**影子规则检测**——高优先级规则完全覆盖低优先级规则的作用范围，使低优先级规则永远不会生效。审计结果在隔离操作前输出警告，确保响应操作不会引入新的安全风险。

## 2.5 CyberReview 攻防复盘引擎

### 2.5.1 攻击时间线构建

在整个安全闭环过程中，CyberReview通过attack-timeline MCP服务器持续记录各阶段的关键事件。时间线覆盖八种事件类型，对应安全闭环的四个阶段：

| 阶段 | 事件类型 | 记录内容 |
|:---:|:------:|:------:|
| 感知 | scan_started / scan_completed | 扫描目标、扫描策略、发现设备数 |
| 检测 | vuln_found / alert_received | CVE信息、告警内容、严重级别 |
| 响应 | attack_detected / response_executed / device_isolated | 攻击判定、执行动作、验证结果 |
| 复盘 | verified | 最终确认和闭环完成 |

所有事件按时间戳顺序组织为时间线，支持按时间范围和按设备维度两种查询方式。时间线数据持久化至SQLite数据库，支持跨会话的历史事件检索。

### 2.5.2 根因分析算法

根因分析旨在从单次攻击事件中提取可复用的防御知识。算法分四步执行：

**（1）入口识别**——以attack_detected事件为锚点，向前回溯24小时的时间线事件，识别攻击的初始入口（如某台摄像头使用默认密码被暴力破解、某台设备存在未修补的CVE漏洞被远程利用）。

**（2）扩散路径构建**——将时间线中涉及的多台设备按攻击时序组织为有向无环图（DAG），节点为受影响设备，边为攻击传播路径，边的权重为攻击利用的漏洞或手法。

**（3）薄弱环节统计**——对时间线中涉及的设备执行CIS基线检查，统计各检查项的违规率。当某项规则的违规率超过50%时标记为“系统性缺陷”（如某网段设备普遍使用默认密码），优先生成修复建议。

**（4）改进建议生成**——综合入口识别、扩散路径和薄弱环节的分析结果，由LLM生成结构化的根因分析报告，包含攻击链还原、防御薄弱点和针对性加固建议。

### 2.5.3 安全报告自动生成

CyberReview支持三种报告类型的自动生成：（1）**incident报告**——聚焦单次安全事件，包含攻击时间线、影响范围和处置记录；（2）**review报告**——侧重防御体系整体评估，包含根因分析和改进建议；（3）**compliance报告**——面向合规审计场景，汇总安全基线达标率和不合规项清单。所有报告由CyberAgent基于事件数据和时间线自动生成，用户可通过自然语言指定类型。

### 2.5.4 闭环反馈机制

闭环反馈是CyberClaw实现"安全能力持续进化"的核心机制。根因分析的结果通过两条路径反馈至感知阶段：一是**知识持久化**——将攻击模式、利用手法和防御薄弱点写入长期记忆库，在后续分析中提供历史参考；二是**策略优化**——根据根因分析发现的系统性缺陷自动调整下一轮感知策略（如某网段设备普遍存在默认密码，则对该网段优先执行默认密码检测），实现"每轮闭环都比上一轮更精准"的自适应安全能力。

## 2.6 CyberAgent AI决策与编排层

### 2.6.1 AI Agent架构

CyberAgent是CyberClaw的智能决策中枢，基于大语言模型Agent架构构建。Agent的核心设计采用"系统提示词（System Prompt）+ 意图编排器（Intent Orchestrator）+ 工具执行器（Tool Executor）+ LLM推理器"四层架构。系统提示词定义Agent的IoT安全分析专业角色、可用工具列表、环境上下文（设备清单、安全状态、事件统计）和严格的操作规范——包括如实反映工具执行结果、按CVSS评分准确评估风险等级、区分工具失败与成功等行为约束。意图编排器负责将用户的自然语言输入解析为结构化的工具调用计划，最多并行触发3个工具组以避免系统过载。工具执行器通过MCP协议调用对应的安全工具获取实际数据。LLM推理器基于DeepSeek大语言模型，将工具返回的原始数据转化为可理解的安全分析报告和操作建议。

三级权限体系确保Agent行为始终在安全边界内：只读操作（扫描/查询/分析）自主执行，写操作（隔离/封禁）须用户确认，破坏性操作（设备重置/批量隔离）完全禁止。权限判定通过隔离确认卡片机制实现——当用户请求隔离操作时，Agent生成包含设备信息和操作详情的HTML确认卡片，用户点击确认按钮后方可执行。

### 2.6.2 ReAct推理循环

CyberAgent的核心推理采用ReAct（Reasoning and Acting）模式。单次ReAct迭代分为三阶段：**Thought**——Agent基于当前证据和上下文，通过LLM生成思维链推理；**Action**——根据推理结论调用对应的MCP工具获取新信息；**Observation**——接收工具返回结果注入上下文，重新评估证据充分性。

> **【图2-8】ReAct推理循环示意图** — 中心为环形箭头循环（Thought→Action→Observation），左侧输入（用户自然语言 + 设备事件），右侧输出（安全报告 + 3D HUD更新 + 响应建议）。循环中心标注“安全约束规则 + Skills编排”。底部展示两条示例路径：高风险路径（7轮完整推理）和低风险路径（3-4轮快速判定）。可复用初赛文档图4。

ReAct模式在安全场景中的核心优势是**动态策略调整能力**——传统的固定流程SOAR无法根据中间结果调整分析路径，而ReAct使Agent能够在每一轮迭代中根据新证据重新规划下一步操作。系统提示词中内置的安全规则约束Agent在每一步推理中的行为边界：如实报告工具执行失败、按CVSS评分准确分级、禁止在无数据时编造结论。配合TOON序列化压缩上下文消耗，单次完整闭环分析（7轮推理）可在15秒内完成。

### 2.6.3 Skills声明式编排

CyberAgent采用声明式的安全技能编排机制。每个Skill描述特定安全场景下的工具调用链和编排逻辑，通过意图-工具映射表（Intent-Tool Map）定义。Skills按安全闭环阶段分为四类：感知类（scan-network、check-default-password）、检测类（anomaly-detect、full-response）、响应类（isolate-device、block-ip）、复盘类（generate-report）。每类Skill绑定一组正则模式，当用户提问或安全事件触发时，意图编排器通过语义匹配定位最相关的Skill，按预定义的调用顺序调度MCP工具并收集结果。

声明式编排的关键设计是**并行工具执行**——同一意图关联的多个工具调用通过asyncio并发执行，将串行的多工具调用耗时压缩为单次最慢工具的耗时。例如"检查网络安全"意图同时触发nmap扫描、IoT指纹识别和默认密码检测三个工具并行执行。编排器还实现了工具调用结果的智能摘要——根据不同工具的返回数据结构（hosts_found/total_cves/devices_audited等字段）自动生成人类可读的分析步骤描述，作为LLM推理的上下文输入。声明式设计使安全分析师无需编程即可通过修改映射表添加新的分析场景。

### 2.6.4 三层记忆架构

为支持跨会话的持续安全分析能力，CyberAgent设计了三层记忆架构：

> **【图2-9】三层记忆架构图** — 三层金字塔结构。底层（最大）：短期记忆Layer 1——chat_history.json对话滑动窗口（500条），存储完整对话历史；中层：工作记忆Layer 2——TaskContext结构化对象，跟踪当前任务的设备信息、扫描状态、中间结论和推理链；顶层（最小）：长期记忆Layer 3——ChromaDB向量数据库，语义检索存储设备知识图谱、历史攻击模式和安全决策记录。三层之间用箭头标注写入和检索流向。

**Layer 1 短期记忆**：基于chat_history.json的对话滑动窗口（上限500条），存储完整的用户- Agent交互历史。新消息追加写入，超出上限时淘汰最早的消息。短期记忆保障多轮对话的上下文连贯性——用户先问“扫描网络”，再追问“那台摄像头有什么漏洞”时，Agent自动将“那台摄像头”解析为第一轮扫描结果中的具体设备。

**Layer 2 工作记忆**：基于TaskContext结构化对象，跟踪当前安全分析任务的执行状态。TaskContext包含：目标设备信息、已执行的工具调用和返回结果、中间推理结论、置信度评估和待执行的后续步骤。工作记忆保障ReAct推理循环中的状态连续性——每一轮推理的结论都写入工作记忆，作为下一轮推理的输入。

**Layer 3 长期记忆**：基于ChromaDB向量数据库的知识持久化引擎。存储内容包括：设备历史安全状态变更、攻击模式知识图谱、安全决策记录和基线审计趋势。支持语义检索——当用户发起安全查询时，Agent通过向量相似度搜索从长期记忆中检索相关的历史分析结论，辅助当前推理决策。长期记忆使系统具备“经验积累”能力，每次安全分析的结果都成为后续分析的参考依据。

### 2.6.5 多Agent协作架构

面对复杂安全事件，单一Agent的能力和上下文窗口可能不足以支撑完整的多源关联分析。CyberClaw设计了多Agent协作架构，通过专业化分工提升分析效率和深度：

> **【图2-10】多Agent协作架构图** — 中心为OrchestratorAgent（编排者），周围三个专业Agent：ScanAgent（感知专家，调用nmap-scan+device-config）、AnalyzeAgent（分析专家，调用cve-intel+security-baseline+flow-analyzer+traffic-analyzer）、ResponseAgent（响应专家，调用auto-response+config-audit）。Orchestrator通过共享上下文总线与三个Agent通信，支持三种编排模式：串行（完整闭环）、并行（多源检测同时进行）和条件分支（根据中间结果动态调整）。

**OrchestratorAgent**（编排者）负责接收用户请求、拆分分析任务、调度专业Agent和聚合分析结果。编排者维护全局上下文，协调各Agent的执行顺序和数据传递。

**ScanAgent**（感知专家）专注网络扫描和设备发现，封装nmap-scan和device-config两个MCP服务器的调用逻辑，输出结构化的设备资产清单。

**AnalyzeAgent**（分析专家）专注安全检测和关联分析，协调cve-intel、security-baseline、flow-analyzer和traffic-analyzer四个MCP服务器，执行多源数据关联和威胁判定。

**ResponseAgent**（响应专家）专注安全响应和配置审计，调用auto-response和config-audit两个MCP服务器，执行隔离操作和规则审计。

协作架构支持三种编排模式：（1）**串行编排**——完整闭环场景，Scan→Analyze→Response依次执行，前一个Agent的输出作为下一个Agent的输入；（2）**并行编排**——多源检测场景，AnalyzeAgent内部同时启动CVE查询、基线审计和流量分析，利用asyncio.gather并行执行缩短分析时间；（3）**条件分支**——动态调整场景，根据AnalyzeAgent的中间结果决定是否触发ResponseAgent，或追加ScanAgent的深度扫描。

### 2.6.6 TOON序列化优化

安全分析涉及大量表格类数据（端口列表、CVE查询结果、路由表等），标准JSON格式在表达这类数据时存在大量冗余的键名重复。CyberClaw采用TOON（Tabular Object Oriented Notation）序列化格式，在MCP工具返回数据时自动编码，相比JSON在表格类数据上节省40%-60%的token消耗。TOON解码失败时安全回退至JSON格式，确保兼容性。所有MCP服务器的返回结果均经过toon_serializer模块处理，对Agent透明，无需修改工具调用逻辑。

### 2.6.7 自然语言交互与意图理解

CyberAgent支持自然语言交互——用户用中文提问，AI自动完成分析并返回自然语言报告。意图理解基于LLM的语义推理能力，将用户的自然语言输入映射到对应的Skill编排流程。系统支持多轮对话的上下文连贯性管理：第一轮扫描结果中的设备清单被保留在上下文中，第二轮提问时Agent自动将代词（“那台摄像头”）解析为具体的IP地址和设备信息，无需用户重复提供。

## 2.7 3D安全可视化

### 2.7.1 Three.js渲染架构

3D安全HUD采用“数据层→事件层→渲染层→交互层”四层可视化架构，代码规模达1,667行核心逻辑。渲染层基于Three.js v0.170 WebGL引擎构建，包含三个核心子系统：

**场景图管理器**负责设备节点、连接线和标签的创建、更新、销毁全生命周期管理。每种IoT设备类型映射到独特的3D几何体——路由器为八面体、交换机为长方体、摄像头为圆锥体、传感器为四面体、充电桩为圆柱体、服务器为高长方体、网关为圆环体，共9种设备几何体，使运维人员可通过形状直觉区分设备类型。

**渲染层次设计**：每台设备渲染为三层叠加效果——底层为暗色实体Mesh底座加自发光状态色，中层为70%透明度的线框外壳，顶层为状态色光环底座。三层渲染确保设备在不同视角和背景下均清晰可辨。

**后处理管线**采用五通道串行渲染架构：RenderPass基础渲染→UnrealBloomPass辉光效果→VignetteShader暗角→GlitchPass故障特效→OutputPass最终输出。场景采用三点布光系统（主光源+暖色补光+冷色轮廓光），配合600粒子星空（带相位闪烁）、三层脉冲光环（自定义Shader）和160×40网格地面，营造科幻风格的网络安全态势感知环境。系统设计三种画质模式：FOCUS模式（日常监控，降低Bloom强度，保持流畅帧率）、BALANCED模式（默认配置，全部特效启用）、BROADCAST模式（增强色差和拖尾效果，适用于演示录制）。

### 2.7.2 设备安全状态可视化模型

CyberClaw设计了**五维安全态势编码模型**，利用三维空间的视觉通道实现安全信息的多维度并行编码：

| 编码维度 | 视觉通道 | 安全语义 | 技术实现 |
|:------:|:------:|:------:|:------:|
| 安全状态 | 节点基色 | 安全(绿)/漏洞(黄)/攻击(红)/隔离(灰)/扫描(蓝) | MeshStandardMaterial.emissive + GSAP渐变 |
| 威胁严重性 | 发光强度 | CVSS评分越高辉光越强 | UnrealBloomPass + emissiveIntensity映射 |
| 威胁紧急性 | 脉冲频率 | 紧急告警脉冲更快 | GSAP缩放动画频率参数化 |
| 流量异常度 | 粒子密度 | 异常流量越大粒子越密 | InstancedMesh粒子数动态调整 |
| 攻击阶段 | 光束颜色 | 侦察(蓝)/利用(橙)/横向移动(红)/C2(紫) | 自定义GLSL着色器uniform参数 |

### 2.7.3 攻防动画效果设计

攻防动画效果使用Three.js的GSAP v3.12动画引擎和自定义GLSL着色器实现，核心特效包括：

- **攻击光束**（CatmullRomCurve3 + 双层管道渲染）：沿设备间连线的粒子流动画，采用30段贝塞尔曲线平滑路径，内核管道（0.12半径）渲染攻击颜色，外层发光管道（0.35半径）产生辉光扩散效果。动画时序：淡入0.3s→保持1.5s→淡出0.8s，模拟攻击流量的时序特征。
- **扫描波纹**（RingGeometry + 扩展动画）：网络扫描时从扫描源向四周扩散的同心环动画，2秒内缩放至30倍并同步渐隐，直观展示扫描范围。
- **隔离护盾**（IcosahedronGeometry线框 + 弹性动画）：设备隔离后覆盖其表面的二十面体线框护盾，采用GSAP back.out弹性缓动产生“弹出”视觉效果，持续旋转动画维持防护状态的视觉提示。
- **故障特效**（GlitchPass全屏后处理）：检测到攻击时触发的全屏RGB偏移和扫描线闪烁效果，0.5秒后自动关闭，用于高优先级告警的视觉冲击。

所有动画通过WebSocket事件驱动——后端推送attack_detected/lateral_movement/c2_detected等25+种事件类型后，前端通过消息类型映射自动触发对应的动画序列和设备状态FSM转换，实现“事件→视觉反馈”的亚秒级响应。

### 2.7.4 WebSocket实时推送

3D HUD与后端通过WebSocket协议实现实时双向通信。设计包含四项关键机制：

（1）**心跳保活与自动重连**——服务端每5秒广播心跳消息，包含全网安全状态统计（各状态设备数量、场景进度、活跃告警数）。客户端采用指数退避重连策略（初始1秒，最大30秒），重连成功后自动请求完整状态同步，确保断线后数据不丢失。

（2）**25+种消息类型的事件驱动架构**——WebSocket消息分为7大类：初始化消息（init/scenario控制）、攻击链事件（attack_detected/lateral_movement/c2_detected）、漏洞扫描事件（port_scan/vuln_found/brute_force）、防御响应事件（device_isolated/threat_resolved）、MCP工具事件（tool_started/scan_result/cve_result/baseline_result）、实时数据流（syslog_event/snmp_trap/mqtt_message/suricata_alert）和心跳同步。每种消息类型映射到特定的3D动画和UI更新操作。

（3）**BroadcastChannel跨窗口同步**——多个浏览器标签页通过BroadcastChannel API共享WebSocket状态和关键数据（告警列表、设备事件、扫描结果、合规分数），避免重复连接，确保任意标签页的操作实时反映到其他标签页。

（4）**localStorage本地持久化**——告警数据、设备事件、扫描结果、合规数据等关键状态同时持久化到localStorage，页面刷新后自动恢复，配合BroadcastChannel实现多标签页数据一致性。

后处理管线设计三种画质模式：FOCUS模式（日常监控，降低Bloom强度，关闭阴影和Film特效，保持流畅帧率）、BALANCED模式（默认配置，所有特效启用）、BROADCAST模式（增强色差和拖尾效果，适用于演示录制）。

## 2.8 MCP安全工具服务层

### 2.8.1 MCP协议与标准化接入

MCP（Model Context Protocol）定义了AI Agent与外部工具之间的标准化连接协议。CyberClaw选择MCP作为工具集成协议基于三方面考量：（1）**标准化**——统一的工具注册、发现和调用规范，新增工具遵循协议即可即插即用；（2）**安全性**——stdio传输不暴露网络端口，无需端口分配和证书管理，在内核空间完成数据拷贝避免网络延迟；（3）**生态兼容**——MCP月度SDK下载量超过9,700万次，社区服务器超过5,800个，便于未来扩展。

MCP协议栈采用JSON-RPC 2.0消息格式通过stdio管道传输，每个MCP服务器作为独立进程运行，通过FastMCP框架（Python 3.10+）暴露工具接口。Agent通过MCP客户端按需发现和调用工具，工具返回结果自动经过TOON序列化优化。

### 2.8.2 十二个MCP服务器设计

12个MCP服务器按安全闭环阶段分为四类，共计约100个安全工具：

| 类别 | MCP服务器 | 工具数 | 核心能力 |
|:---:|:-------:|:-----:|:------:|
| 感知 | nmap-scan / device-config / simulation | 6/13/30+ | 多模式扫描、IoT指纹识别、默认密码检测、gNMI/SSH配置管理、GNS3仿真 |
| 检测 | syslog-collector / snmp-collector / cve-intel / security-baseline / flow-analyzer / traffic-analyzer | 6/6/4/4/7/4 | RFC5424日志解析、SNMP v1/v2c/v3、NVD CVE查询（含CPE构造）、CIS基线审计（53条规则）、IPFIX v5/v9/v10解析、tshark深度包检测 |
| 响应 | auto-response / config-audit | 6/4 | iptables/SSH双模式隔离、ACL封禁、效果验证、回滚、配置合规审计 |
| 复盘 | attack-timeline | 4 | SQLite持久化时间线、攻击链DAG重建、根因分析、报告生成 |

### 2.8.3 工具动态加载与反射机制

MCP服务器采用运行时动态加载机制。系统启动时读取配置文件获取所有MCP服务器的注册信息，通过反射机制自动发现和注册每个服务器暴露的工具函数。这一机制使新增MCP服务器无需修改任何加载代码——只需编写服务器文件并更新配置即可自动发现和注册。服务器之间无状态耦合，任意服务器的故障不影响其他服务器的正常运行。动态加载的具体实现机制见第三章。

## 2.9 系统安全架构

### 2.9.1 认证与授权体系

CyberClaw设计了JWT Token + API Key双因素认证体系。用户登录时通过用户名/密码验证获取JWT Token（有效期24小时），后续API请求携带Token进行身份验证。系统间集成（如3D HUD与后端的WebSocket连接）使用API Key进行服务级认证。三级权限体系控制操作范围：read-only（只读，仅允许扫描和查询操作）、write-with-confirmation（写操作需确认，允许隔离和封禁但须经用户授权）、prohibited（禁止，危险操作完全禁止执行）。

### 2.9.2 敏感数据保护

敏感数据保护采用多层加密策略。设备连接凭据（SSH密码、SNMP community string）使用Fernet对称加密存储于本地配置文件，密钥通过环境变量注入，不硬编码于代码中。API通信使用HTTPS加密传输。数据库中的敏感字段（如设备IP与漏洞的关联关系）采用字段级加密。日志输出自动过滤敏感信息（密码、Token等），确保审计日志不泄露敏感数据。

### 2.9.3 隔离操作安全机制

隔离操作是CyberClaw中影响最大的安全响应动作，设计了四重安全保障：（1）**Confirmation Token机制**——每条隔离指令携带一次性confirmation_token，防止重放攻击；（2）**关键设备白名单**——标记为"关键"的设备（如核心交换机、网关）即使检测到攻击也须二级确认后方可隔离，避免误操作导致全网中断；（3）**超时自动恢复**——每条隔离操作设置可配置的超时时间（默认1小时），超时后自动回滚，防止设备长期被误隔离；（4）**GAIT审计日志**——所有隔离操作记录至JSON Lines格式的审计日志，包含操作者、时间戳、目标设备、操作原因和执行结果，满足《网络安全法》六个月日志留存要求。

### 2.9.4 安全通信与合规

系统组件间通信遵循最小权限原则：后端API服务仅暴露必要端口（8000），CORS配置限制允许的来源域名，WebSocket连接通过Token认证。满足等保2.0物联网安全扩展要求中的感知网接入控制、入侵防范和网关节点设备安全等控制点。

## 2.10 双模运行与调度系统

### 2.10.1 双模自动切换

CyberClaw同时支持两种工作模式并实现自动切换。**实时监控模式**面向7×24小时不间断监控需求，事件驱动自动触发检测链——设备事件到达后经阈值过滤，自动匹配anomaly-detect Skill启动关联分析。**交互问答模式**面向安全人员日常交互需求，用户自然语言提问驱动分析流程。两种模式共享同一套安全引擎和Skills编排逻辑，确保分析结果一致。当监控模式检测到攻击并生成响应建议后，用户可无缝切换到问答模式对建议进行调整（如“只隔离这台设备，不要封禁整个网段”），实现自动化与人工决策的平滑衔接。

### 2.10.2 安全任务调度器

基于croniter的安全任务调度器支持三种调度模式：（1）**一次性任务**——指定时间执行一次（如"明天凌晨3点全网扫描"）；（2）**周期性任务**——cron表达式定义执行周期（如"每天8:00扫描一次"）；（3）**预设模板**——内置5个安全巡检任务（每日端口扫描、每周CVE更新、每月基线审计等）。任务配置持久化至JSON文件，支持运行时动态添加、修改和删除。调度器与CyberAgent集成，任务执行结果自动推送至3D HUD和对话通道。

### 2.10.3 多通道通知系统

通知系统提供四通道告警推送能力：（1）**ntfy推送**——通过ntfy开源推送服务向移动端发送告警通知；（2）**Webhook集成**——HMAC签名验证的Webhook推送，支持与企业IM（钉钉、飞书、企业微信）集成；（3）**WebSocket广播**——实时推送至3D HUD进行可视化展示；（4）**Chat内嵌**——在自然语言对话通道中生成告警摘要。通知系统实现告警去重（相同设备的重复告警在时间窗口内合并）和告警升级（持续未处理的告警自动提升严重级别并扩大通知范围）。
